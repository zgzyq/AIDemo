# Review

## 什么时候用

- 功能、脚本或文档改动已经接近完成
- 想在结束前做一次更工程化的 review gate
- 用户要过一遍风险或看看还有什么问题

## 不什么时候用

- 需求仍未定，应先走 `office-hours` 或 `plan-eng-review`
- 还没开始实现或验证

## 默认步骤

1. 先读这轮目标、范围、改动点和验证结果。
2. 用 findings-first 方式输出问题，优先级从高到低。
3. 区分：
   - 必修问题
   - 建议优化
   - 已接受风险
4. 如果没有问题，也要说明验证缺口或剩余风险。

## 输出要求

- 先列问题，再给简短结论
- 能给文件/位置就给
- 没问题时也不能只写“看起来可以”
